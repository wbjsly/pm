## Context

SRS（FR-PM-021）定义的预算制定功能已有数据库迁移脚本（`014-pm-cost.sql`），但 Java 层和前端层完全未实现。预算功能独立于 WBS 管理，不依赖 WBS 数据。

当前已有的基础设施：
- Flowable 审批引擎（已有 `PM_CHARTER_APPROVAL` 流程）
- 审批回调机制（`ApprovalCompletedCallback` + `ApprovalCallbackRegistry`）
- SequenceService 流水号生成
- SqliteBootstrap SQL 迁移框架
- MyBatis-Plus ORM + BaseEntity 模式

## Goals

1. 实现完整的预算编制能力（两级科目，手动逐条添加）
2. 预算走独立 Flowable 审批流，动态审批人
3. 实现预实对比分析（严格按预算科目行一一对应）
4. 实现成本预警机制（定时任务 + Dashboard 集成）
5. 实际成本支持手动录入兜底 + 事件总线接口（为后续模块对接预留）

## Non-Goals

- 不实现工时/采购/报销系统的自动对接（预留接口，后续模块完成后对接）
- 不实现预算模板导入功能（手动逐条添加）
- 不实现复盘流程（线下进行，系统内仅关闭预警）
- 不实现站内消息推送（预警通过 Dashboard 卡片和预警列表展示）

## Decisions

### D1: 预算科目模型 — 方案 B（统一骨架表 + 拆子表）

**决策**: 使用 `pm_budget_item` 作为统一科目骨架表，人工/采购/其他分别用子表存储扩展字段。

**理由**: 
- 骨架表支持所有 7 个一级科目，查询汇总时只需查一张表
- 子表存储特有字段（人工的角色/工时/定额、采购的 BOM/数量/单价）
- 差旅/商务/招待/活动/其他共用 `pm_budget_item_other`，通过 CATEGORY 区分
- 扩展性好（新增科目不用改骨架表，只需加子表或复用 other 表）

### D2: 预算版本规则 — 递增式版本号

**决策**: v0.1(草稿) → v0.7(提交) → v1.0(审批通过) → v1.1(调整草稿) → v1.7(调整提交) → v2.0(调整审批通过)

**理由**:
- 整数位直观反映审批次数
- 小数位反映当前阶段（1=草稿, 7=已提交, 0=已审批）
- 审批通过后锁定，修改必须创建新版本
- 同一项目同一时刻只有一个 APPROVED 版本

### D3: 预算审批流 — 独立 BPMN + 动态审批人

**决策**: 新建 `PM_BUDGET_APPROVAL` 独立流程，审批人从项目章程 SPONSOR_ID 获取。

**理由**: 预算审批独立于章程审批，且预算可能在项目过程中多次调整。

### D4: 实际成本归集 — 占位模式 + 事件总线

**决策**: 实现 `CostEventPublisher` 接口和 `pm_actual_cost.budget_item_id` 外键，手动录入兜底。

**理由**: 工时/采购/报销系统尚未实现，手动录入满足当前需求，事件接口为后续自动化对接预留。

### D5: 实际成本取值状态 — 提交状态

**决策**: 取工时/采购/报销单的提交（SUBMITTED）状态，不取审批通过状态。

**理由**: SRS 明确要求"取提交状态的"。

### D6: 预警触发 — 定时任务 + 全局配置

**决策**: Spring `@Scheduled` 定时任务，执行时间通过 `application.yml` 全局配置。

**理由**: 简单可靠，全局配置避免按项目配置的复杂度。

### D7: 预实对比 — 严格一一对应

**决策**: 实际成本行严格按预算科目行一一对应，通过 `budget_item_id` 关联聚合，无数据则为 0。

**理由**: 保证对比的准确性和可读性，避免遗漏科目。

### D8: 预实对比版本切换 — 支持历史版本

**决策**: 默认展示最新 APPROVED 版本，支持下拉切换历史版本。

**理由**: 审计和追溯需要。

### D9: 预警通知 — Dashboard 卡片 + 预警列表

**决策**: 不做站内信推送，所有预警通过 Dashboard 预警卡片和预警列表页面展示。

**理由**: 项目暂无消息中心，避免引入额外复杂度。

### D10: OpenSpec 拆分 — 一个 change

**决策**: 整个 FR-PM-021 作为一个 change `fr-pm-021-budget`，不拆分。

**理由**: 预算编制 ↔ 预实对比 ↔ 预警是完整闭环，拆分后跨 change 依赖反而增加复杂度。

## Risks

| Risk | Impact | Mitigation |
|------|--------|------------|
| `pm_budget_item` 子表 JOIN 查询性能 | 低 | SQLite 数据量不大，且预算科目数量有限 |
| 成本事件总线接口后续模块对接不一致 | 中 | 明确定义 `CostEvent` 契约，后续模块按契约实现 |
| 定时任务在大量项目场景下执行慢 | 低 | 初期项目数量有限，后续可优化为增量计算 |
| 预算科目树编辑体验复杂 | 中 | 首期手动逐条添加可接受，后续可加导入功能 |

## Migration Plan

1. 新增 DDL 迁移脚本（`024-pm-budget-item.sql`）
2. 扩展 `pm_actual_cost` 表（`ALTER TABLE`）
3. 创建所有 Entity/DAO/BO/Controller
4. 创建 BPMN 流程定义
5. 创建前端页面和 API
6. 集成 Dashboard 预警卡片
